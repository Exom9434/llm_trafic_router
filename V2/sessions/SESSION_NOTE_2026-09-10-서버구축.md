# 2026-09-10 측정 서버를 서울 리전에 확보하고 데이터센터 IP를 검증했다

### 한 줄 요약

본실험 측정 지점을 윈도우 랩탑에서 AWS Lightsail 서울 인스턴스로 옮겼다. 배포 절차를 저장소에 넣고 스모크 테스트로 여덟 모델이 데이터센터 IP에서 정상 응답하는 것을 확인했다. 이번 단계의 관문은 통과했다.

같은 날 다른 세션과 파일명이 겹쳐 이 노트가 한 번 덮였다. 그래서 날짜 뒤에 주제를 붙이는 이름으로 바꿔 다시 썼다.

### 제공사 선정

Lightsail 서울(ap-northeast-2) $7 등급. 2 vCPU / 1GB RAM / 40GB SSD / 2TB 전송. 고정 IP는 3.34.88.19.

선정 기준을 가격에 두지 않았다. API 예산이 205달러인데 서버는 한 달에 5달러에서 7달러다. 반면 하루라도 슬롯이 빠지면 그날이 완주 실패로 배제되므로(8.1절), 기준은 21일 동안 멈추지 않는 쪽이다.

Oracle 무료 티어를 뺐다. 2026년 7월에 Ampere A1 한도가 절반으로 축소되었고 유휴 판정 회수 정책이 살아 있어 무인 실행 중 인스턴스가 소멸할 여지가 있다.

Vultr 서울이 5달러로 더 싸지만 고르지 않았다. 인프라 자체는 문제가 없으나 계정과 결제 쪽 정지 사례가 저가 VPS 커뮤니티에서 반복 보고된다. 21일 무인 실행에서 확률이 높은 실패는 하드웨어 고장이 아니라 계정이 잠겨 인스턴스가 멎는 쪽이다. 2024년 4월 이용약관 논란도 감점 요인이었다.

Lightsail의 실체는 EC2 인스턴스이며 요금을 번들로 묶고 콘솔을 단순화한 계층이다. 버스터블 인스턴스라 기준선 이상의 CPU 사용은 지속되지 않으나, 러너가 하는 일이 네트워크 대기라 문제가 되지 않는다. 실행 중 CPU가 기준선을 계속 넘으면 그것은 부하가 아니라 재시도 폭주의 신호로 읽는다.

### 배포 절차

`V2/deploy/`를 신설하고 `README.md`와 `bootstrap.sh`를 넣었다. `V2/runner/requirements-run.txt`도 새로 만들었다.

실행용 의존성을 분리했다. `pyproject.toml`이 `datasets`를 정규 의존성으로 잡고 있으나 그것을 쓰는 것은 `itembank.py` 하나이고, 하는 일은 MMLU-Pro 원본에서 후보 풀을 만드는 것이다. 문항 은행은 `data/item_bank.json`으로 확정되었으므로 측정 서버에서 그 경로가 다시 돌 일이 없다. `datasets`를 빼면 pyarrow 묶음이 따라오지 않아 1GB 인스턴스의 설치 부담이 줄어든다. 서버에 올리는 것은 requests와 python-dotenv 둘이다.

`bootstrap.sh`는 패키지 설치, 스왑 1GB, 시간대 UTC 고정과 chrony 동기 확인, 가상환경, 산출물 디렉터리 생성, 배치 확인, 키 점검을 한 번에 한다. 스왑을 넣은 이유는 램 1GB에서 재시도가 몰릴 때 OOM으로 프로세스가 죽으면 그날이 완주 실패가 되기 때문이다. 시간대를 UTC로 고정한 이유는 슬롯 라벨이 UTC 시각으로 정해져 시계가 틀리면 조건 배정이 틀리기 때문이다.

코드 전송은 rsync로 한다. 저장소에 46MB 보정 로그와 3월 벤치마크 CSV가 있어 통째로 올릴 이유가 없다. 서버가 실행 시점에 읽는 것은 `.env`, `V2/runner/` 코드, `data/item_bank.json`, `capabilities.json` 넷이며 전송량은 2MB 남짓이다.

`.env`가 git에 없으므로 rsync가 유일한 경로다. `git clone`으로는 키가 따라오지 않는다.

### 산출물 디렉터리 누락

첫 스모크 테스트가 마지막 줄에서 넘어졌다. rsync에서 `outputs/`를 제외했는데 스크립트가 보고서를 그 경로에 쓴다. API 콜은 전부 끝난 뒤였고 `capabilities.json`도 저장된 상태였으므로 손실은 없었다. `bootstrap.sh`에 `mkdir -p` 단계를 넣어 재발을 막았다.

코드가 환경에 대한 가정을 조용히 품고 있던 사례다. 개발 머신에는 그 디렉터리가 늘 있었으므로 로컬에서는 드러나지 않는다.

### 스모크 테스트 결과

여덟 모델 전부 OK, 답은 전부 C, 인증이나 rate limit으로 막힌 곳은 없다. 서울 데이터센터 IP에서 제공사가 가정용 회선과 다르게 응답하지 않는다는 것이 확인되었다. 이번 단계에서 확인하려던 것이 이것이다.

qwen의 logprob 거절도 로컬과 동일하다.

`capabilities.json`과 `outputs/smoke_test.md`가 서버에 새로 생성되었다.

### 라인업 여덟이라는 오진

check_env가 8/8을 출력한 것을 두고 `upstage_solar_pro3`가 서버에서 누락되었다고 판단했으나 오진이었다. `config.py`에 `RETIRED` 리스트가 따로 있고 업스테이지가 거기 들어 있다. `ALL_MODELS = LINEUP + ANCHORS`이므로 어떤 실행에도 포함되지 않는다. 2026-09-01에 제외한 모델이다.

로컬 `outputs/smoke_test.md`에 업스테이지 행이 남아 있는 것은 그 파일이 제외 결정 이전 실행분이기 때문이다. 서버 결과와 대조할 때 이 파일을 현재 라인업의 기준으로 쓰면 안 된다.

키 길이 대조에서 나온 41자 대 39자 차이도 실체가 없다. 로컬 `.env` 값이 따옴표로 감싸여 있고 dotenv가 그것을 벗긴 결과다.

### 기록해 둘 두 가지

DeepSeek의 반환 모델 문자열이 로컬 `deepseek-v4-flash`에서 서버 `deepseek-flash`로 바뀌었다. 09-10 노트에서 탐색 항목으로 세운 버전 변경 탐지가 보려는 신호가 이것이다. 다만 교체 근거로 삼으려면 fingerprint 변경이 함께 관측되어야 하고, 지금은 측정 지점 이동과 섞여 있어 두 원인을 가르지 못한다. 본실험 로그에서 다시 본다.

지연이 제공사마다 방향을 달리해 이동했다. 네이버가 439에서 1438ms로 늘고 DeepSeek이 1211에서 513ms로 줄었다. 콜 한 방씩이라 결론은 이르나, 측정 지점이 바뀌면 지연 기준선이 통째로 이동한다는 것은 분명하다. 지연 프로브에서 보정 측정의 지연 값을 기준선으로 그대로 쓸 수 없다.

### 현재 서버 상태

측정 지점은 확보했고 발신 경로는 검증했으나 측정은 시작하지 않았다.

서버에서 상시 실행 중인 것은 sshd, chrony, systemd 같은 OS 데몬뿐이다. 러너는 상시 프로세스가 아니며 스모크 테스트도 명령을 칠 때 잠깐 떴다 사라졌다. 구동 중인 서버가 아니라 스크립트를 한 번 돌려 본 서버다.

상시 실행이 되려면 셋이 필요하다. 슬롯을 도는 진입점, 그것을 systemd가 소유해 재시작과 부팅 시 기동을 맡는 구성, 그리고 슬롯 카운터를 파일에 남겨 재시작에도 이어지게 하는 장치다. 세 번째는 카운터를 날마다 초기화하면 묶음 0이 미국 피크를 통과하지 못하는 문제와 같은 것이며, 프로세스 재시작도 같은 결과를 낸다.
