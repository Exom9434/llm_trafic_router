# 2026-09-11 지연 프로브가 재던 것이 지연이 아니었음을 확인하고 고쳤다

### 한 줄 요약

측정 서버에서 스트리밍 점검을 처음 돌렸더니 여덟 중 셋이 걸렸다. 파고드니 원인이 하나가 아니라 셋이었고, 셋 다 TTFT를 지연이 아닌 다른 값으로 만들고 있었다. 고친 뒤 여덟 모델 전부 3초 아래로 들어왔다.

어제 노트에서 다음 할 일로 세운 스케줄러와 지연 프로브 중 지연 프로브 쪽이다.

### 점검을 따로 돌린 이유

`experiment.py`의 `probe_streaming()`이 실행 시작 때 모델마다 스트리밍 가부를 한 번 정하고 21일 내내 유지한다. 중간에 방식이 바뀌면 그 모델의 지연 곡선에 계단이 생기기 때문이다. 여기서 모델별 TTFT가 한 번씩 찍히므로 이 출력이 곧 점검 결과다.

`--dry-run`은 예산 계획을 읽고 바로 반환해 이 지점에 닿지 않는다. 본실행을 걸면 슬롯이 실제로 발사된다. 그래서 `probe_streaming`만 따로 불렀다. 모델당 한 콜에 64토큰이라 로그도 예산 원장도 건드리지 않는다.

### 첫 결과와 세 갈래

deepseek가 스트리밍 불가로 떨어지고, qwen이 13분을 매달렸다가 TTFT 36,960ms로 통과했다. 나머지 여섯은 정상으로 보였다.

세 가지가 겹쳐 있었다.

**추론 토큰을 델타로 세지 않음.** `_stream_event`가 `delta.content`만 읽었다. deepseek v4-flash는 추론을 끌 방법이 없고 같은 문항에 53~72토큰을 쓴다. 지연 프로브 상한이 64라 추론이 예산을 다 먹고 본문이 한 줄도 나오지 않았다. 스트림은 정상으로 흐르는데 델타가 계속 빈 문자열이라 TTFT가 None으로 남았고, 프로브가 그것을 스트리밍 불가로 읽었다. 원시 응답을 덤프해 확인했다. HTTP 200에 `content:null`, 토큰은 전부 `reasoning_content`다.

같은 결함이 qwen에서는 다르게 나타났다. 추론 430~457토큰이 끝나야 첫 본문 토큰이 나오므로 TTFT가 추론 시간을 통째로 포함했다. 추론 길이는 이 연구가 재려는 품질 지표다. 지연 지표가 품질 지표에 오염되면 피크에 TTFT가 늘어도 혼잡 때문인지 더 길게 생각해서인지 가를 수 없다.

**stream_options에 무응답.** qwen이 `stream_options: {include_usage: true}`를 400으로 거절하지 않고 연결만 열어 둔 채 아무것도 보내지 않는다. 총 소요시간 상한 180초에 재시도 4회가 물려 콜 하나가 12분을 태운다. 13분의 정체가 이것이다.

`openai_compat.py` 주석은 러너가 시작 점검에서 이 값을 내리고 다시 시도한다고 적혀 있었으나, 그 강등은 시작 점검이 만든 어댑터 인스턴스에만 남는다. `core.py`가 슬롯마다 어댑터를 새로 만들므로 본실행에서는 매번 다시 붙는다. 슬롯마다 12분을 태우고 qwen의 TTFT가 21일 내내 결측이 될 뻔했다.

**max_tokens가 본문만 자름.** thinking이 켜진 qwen에서 `max_tokens`는 최종 답만 자르고 추론은 건드리지 않는다. 상한 64에 출력 24,960이 나왔고 그중 추론이 24,892, 본문이 68이다. 본문에는 상한이 정확히 걸린 것이다. 품질 프로브의 상한 8,192에 관측 8,728도 같은 구조이며 초과분 536이 추론 몫이다. config 주석이 이것을 모델이 상한을 무시한다고 적어 두었던 것은 틀렸다.

콜당 224.7초였다. 동시성 4에 슬롯당 5회면 4.7분이고, 지연 프로브가 슬롯 맨 앞에 쏘므로 qwen의 품질 콜 300개가 매 슬롯 그만큼 밀린다. 더 위험한 것은 224초가 qwen의 읽기 타임아웃 300초에 붙어 있다는 점이다. 피크에 처리량이 떨어지면 타임아웃이 나고, 결측이 부하와 상관되어 8.1절이 막으려던 절단이 그대로 돌아온다. 비용도 840콜 기준 $0.01에서 $2.73으로 뛴다.

### 고친 내용

```
providers/openai_compat.py   _stream_event가 reasoning_content도 첫 토큰으로 센다
config.py                    ModelSpec.stream_usage, qwen은 False
providers/openai_compat.py   _stream_payload가 스펙 값을 함께 본다
config.py                    ModelSpec.latency_max_tokens_param
config.py                    qwen은 max_completion_tokens
providers/openai_compat.py   _stream_payload가 지연 프로브에서만 키를 갈아 끼운다
config.py                    max_tokens 관련 주석 정정
providers/base.py            폭주 가드
selftest.py                  점검 8건
```

상한 파라미터는 둘을 실측해 골랐다. `max_completion_tokens=64`는 출력이 정확히 64로 떨어지고, `thinking_budget=64`는 추론만 묶어 본문이 따로 붙어 총 131이 된다. 지연 프로브가 원하는 것은 상수 작업량이므로 총량을 묶는 쪽을 썼다. 본문이 0이 되지만 TTFT는 추론 델타로 잡히고 여기서는 답을 채점하지 않는다.

품질 프로브는 손대지 않았다. 거기서 추론을 자르면 주력 지표가 깎인다. 지연 전용 파라미터를 따로 둔 이유가 이것이다.

폭주 가드는 작업량 통제가 아니라 안전장치다. 청크 하나가 토큰 하나가 아니므로 정확한 상한으로 쓸 수 없고, 서버 상한이 도는 한 발동할 일도 없다. 상한의 4배로 두어 정상 운용에는 걸리지 않고 상한을 안 지키는 프로바이더가 또 나왔을 때만 끊는다. 21일 무인 실행에서 그런 일이 나면 아무도 보고 있지 않다.

### 기준선에 관한 판단

측정 지점을 옮기면 지연 기준선이 통째로 이동한다는 어제 관찰 때문에 기준선 측정을 선행 작업으로 잡을지 검토했고, 잡지 않기로 했다. 설계서 3.1절이 프로바이더 내 종단 비교라 네이버의 기준선은 네이버의 오프피크 슬롯이고, 같은 서버에서 같은 21일 동안 찍히므로 측정 지점 효과가 피크와 오프피크에 똑같이 얹혀 차분에서 상쇄된다. 4.1절 노이즈 바닥선도 저부하 슬롯이 담당한다.

어제 노트가 경고한 것은 랩탑에서 잰 보정 패스의 지연 값을 서버 지연의 비교 기준으로 끌어다 쓰지 말라는 것이다. 분석 코드가 보정 로그와 본실험 로그의 지연을 한 축에 올리지 않게만 하면 된다.

### 기록해 둘 것

deepseek의 `system_fingerprint`가 `aeb56401ca74e127821c4f9126dcb669`로 관측되었다. 반환 모델 문자열은 `deepseek-flash`다. 어제 버전 변경 탐지의 조건으로 세운 fingerprint가 실제로 온다는 것이 확인되었고 이 값이 기준점이 된다. 본실험 중에 바뀌면 모델이 갈렸다는 신호다.

qwen의 `capabilities.json` 기록도 확인했다. `top_logprobs` 허용 범위가 [0, 5]인데 그보다 크게 보내 400이 났던 것이며, 현재 `supports_logprobs`는 no로 확정되어 있어 요청에 붙지 않는다.

`outputs/experiment_state.json`의 `start_day`가 2026-09-11로 박혀 있다. 테스트 실행이 만든 것이고 git에도 올라갔다. 이 파일이 있으면 `load_state()`가 새로 만들지 않으므로 10월에 본실험을 시작해도 슬롯 번호의 기준점이 9월 11일이 된다. 주기의 서로소 성질은 깨지지 않으나 기준점이 실제 첫날과 어긋나므로 본실행 직전에 서버와 로컬 양쪽에서 지운다.

### 중간에 한 번 헛짚은 것

고친 뒤 첫 재측정에서 deepseek가 여전히 불가로 나왔다. 코드가 서버에 안 올라간 것이었고 `push.sh`를 안 돌린 상태였다. 같은 파일의 다른 수정이 먹은 것처럼 보이는 착시가 있어 원인을 코드에서 찾을 뻔했다. 서버 파일을 직접 grep해 갈랐다. 측정 서버로 옮긴 뒤로는 로컬 수정과 서버 상태가 갈라질 수 있으므로 재측정 전에 푸시 여부를 먼저 본다.

### 사전등록에 적을 것

지연 프로브의 측정 정의가 확정되었다. TTFT는 본문이든 추론이든 첫 토큰이 도착한 시각이고, 작업량은 추론을 포함한 출력 64토큰으로 고정하며, 그 상한을 거는 파라미터는 프로바이더마다 다르다. qwen은 `max_completion_tokens`, 나머지는 `max_tokens`다. 이 차이를 등록문에 적어야 재현이 된다.

스트리밍 가부도 여덟 전부 가능으로 확정되었으므로 지표 가용성 표에 반영한다.
