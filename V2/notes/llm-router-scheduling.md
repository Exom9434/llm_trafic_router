## 용어 (2026-08-25 결정)

문서와 러너 출력에서는 **"저부하 시간대"**로 쓴다. 이전에 쓰던 "창"(window)은 한국어로 잘 안 읽혀서 바꿨다. `EXPERIMENT_DESIGN.md`, `runner/README.md`, `calibrate.py` 출력 문구를 정리했다. `SESSION_LOG.md`의 과거 항목은 기록이므로 그대로 뒀다.

**코드 식별자는 `window`를 유지한다** — `CALIBRATION_WINDOWS_KST`, `in_window()`, `check_window()`, `wait_until_window()`. 이름을 바꾸면 config·calibrate·selftest로 번지는데 얻는 게 없다.

## 브리지 VM 시계는 UTC다 (2026-08-25에 한 번 틀림)

`device_bash`의 `date`는 UTC를 돌려준다. 여기에 "KST"를 붙여 읽으면 9시간 어긋나며, 실제로 16시를 07시로 잘못 보고한 적이 있다. **반드시 `TZ=Asia/Seoul date`로 확인할 것.** 러너 코드는 `datetime.now(KST)`로 고정 오프셋을 쓰므로 영향이 없다.

## 소요 기간 (2026-08-22 산정)

본실험 14일이 사실상 전부다. 기계 시간은 짧다.

| 단계 | 소요 |
|---|---|
| 키 발급·세팅 + smoke test | 1~2시간 (사람 시간) |
| 보정 패스 | 지역 배치당 24분~1시간 40분 |
| select_bank + budget | 즉시 |
| 본실험 | 14일 (설계 고정) |

- 보정 패스 병목은 HyperCLOVA(`max_concurrency=2`). 다른 모델은 4.
- **배치 크기는 균등하지 않다**(dry-run 실측, 문항 720 기준): 미국 15,840콜(48%) · 중국 8,640 · 한국 8,640. 미국이 시간대는 7시간으로 가장 짧은데 콜은 가장 많다.
- 본실험 슬롯 하나 = 라인업 각 500콜, 4~17분. 슬롯 간격 3시간 대비 **11~43배 여유**.
- 본실험 총 420,000콜, 하루 평균 30,000콜.
- **달력 기준 16~18일을 잡을 것.** 설계가 세는 건 완주한 날 14개다. [[llm-router-budget-guard]] 참조.

## 핵심 발견: 9개 모델이 동시에 한가한 시각은 없다

| 지역 | 프로바이더 | 피크(KST) | 저부하 시간대(KST) |
|---|---|---|---|
| us | OpenAI, Google, Anthropic | 22~06시 (미국 업무시간) | **10~17시** |
| cn | DeepSeek, Qwen | 10~13, 15~19시 (DeepSeek 공표) | **23~07시** |
| kr | Upstage, Naver | 09~18시 | **23~07시** |

cn과 kr의 시간대가 겹쳐 실제로는 두 배치면 된다.

### 보정 패스에는 문제 → 지역별 분할로 해결

어떤 모델의 노이즈 바닥선을 그 모델의 피크 시간에 재면 바닥선 자체가 이미 부하를 먹은 값이 된다. 본실험에서 대비가 줄어 결과가 귀무가설 쪽으로 편향된다. 설계서 6.1절.

### 본실험에는 오히려 유리 → 위약 대조군

관측된 저하가 측정 환경의 잡음이라면 모든 모델에서 **같은 시각**에 나타나야 한다. 반면 각 모델의 저하가 그 프로바이더의 **지역 업무시간을 따라간다면** 공통 시각 요인으로 설명할 수 없다. 서로 반대 방향의 예측이라 검정이 성립한다. 설계서 8.2절. 본실험은 지역별로 나누지 않는다.

## `--wait` 자동 대기 (2026-08-25 구현, 커밋 ed31cbc)

`config.py`에 `wait_until_window()` + `seconds_until_window()` / `seconds_left_in_window()` / `_seconds_to_next_start()`. `calibrate.py`에 `--wait`와 `--min-remaining`(시간 단위). selftest 15건 추가(자정 넘는 구간, 남은 시간 계산, 가짜 시계로 도는 대기 경로 셋).

```bash
uv run calibrate.py --region cn --k 5 --wait                    # 23시에 시작
uv run calibrate.py --region kr --k 5 --wait                    # 이어서
uv run calibrate.py --region us --k 5 --wait --min-remaining 2  # 다음 날 10시
```

**야간 배치를 앞에 둘 것.** `us`를 먼저 두면 다음 날 10시까지 기다리느라 그날 밤을 통째로 버린다.

설계 요점:
- **`--min-remaining`이 핵심이다.** "열려 있지만 곧 닫히는" 경우를 잡는다. 없으면 1분 남아도 시작하고 대부분의 콜이 시간대 밖으로 나간다. 미국 배치는 15,840콜인데 시간대가 7시간뿐이라 2시간을 권장한다.
- **미리 계산한 대기 시간을 믿지 않는다.** 60초마다 현재 시각을 다시 본다 — 랩탑이 절전에서 깨면 시계가 튄다.
- **30분마다 생존 신호를 남긴다.** 로그가 조용하면 멈춘 것인지 자는 것인지 구분할 수 없다.
- **`calibrate.py`가 아니라 `config.py`에 뒀다.** 본실험 스케줄러가 슬롯 대기에 그대로 쓴다. 리허설에서 검증한 코드를 14일 실행이 쓰게 하려는 것.
- `--wait`은 한 시간대만 기다린다. 여러 지역이 섞이면 거부하고 `--region`을 안내한다.

## 남은 자동화 과제

- **본실험 스케줄러(로드맵 3단계, 미구현)** — OS Task Scheduler가 아니라 프로세스 내부 스케줄러(V1의 APScheduler 방식). 하루 8슬롯·3시간 간격 구조는 DeepSeek 공표 피크 경계가 정한 것이라 **tau와 무관** → 보정 패스 결과를 기다릴 필요 없이 설계 가능. 대기 부분은 `wait_until_window()`를 재사용한다.
- **감시 공백(미구현)** — 프로젝트에 알림·하트비트 코드가 하나도 없다. `day_status.jsonl`에 complete/aborted가 남지만 읽는 건 사람뿐이라, 3일차 중단을 랩탑 열어 보기 전엔 모른다. 필요한 것 셋: 재부팅 후 자동 재시작, 하루 요약 알림(완주 여부·모델별 지출·파싱 실패율), **침묵 감지**(N시간 로그가 안 늘면 알림 — 러너는 실패보다 조용히 죽는 쪽이 흔하다).
